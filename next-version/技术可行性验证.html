0结论

技术方向可行，可以继续做；但还不能说"所有板块都已验证"。准确的状态是：地图和外部数据源已经实测，其余板块完成了方案筛选，核心的行程生成和实际部署还没验证。架构思路：大陆用户的浏览器只访问我们自己的域名，海外数据（地图、地点、天气、百科图片）由后端获取并缓存，大模型用国内厂商的接口。

  • 已实测，有原始记录 罗马城区底图自托管渲染；沿街道的步行路线（步行 / 驾车对照确认）；地点坐标、中文名、营业时间；天气预报与历史同期气候；中文维基摘要。请求地址和原始响应存在 tech-spike/raw/。
  • 方案已选，未验证 行程生成（最关键）、截图识别、后台任务的恢复与重试、导出（尤其地图能否导出进长图）、地点库建库流程。大模型接口目前只确认了服务在线（返回 401），不代表调用和输出可用。
  • 需部署后验证 大陆网络下的访问速度、完整生成流程、在微信里打开的表现。当前网络经美国出口，无法代测。
  • 需要调整设计 ① 建"城市地点库"，但它不能保证坐标和营业时间都可靠，需要整理核心景点；② 公共交通只能估算；③ 餐厅没有评分；④ 微信里不能下载文件。详见第 3 节。

1整体架构

手机 / 电脑浏览器网页（H5），不做 App 和小程序
→
自己的域名前端页面、JS、字体、地图底图文件，全部自托管，不引用任何境外 CDN
→
后端（香港服务器）生成任务、地点库、缓存；代理访问海外数据
→
外部服务国内大模型（DeepSeek / 通义 等）· OSM 地点与路线 · Open-Meteo 天气 · 维基百科

香港服务器同时能访问国内大模型和海外数据源，且不需要 ICP 备案，适合作品阶段。代价是大陆访问速度不如国内服务器，需要上线后实测（第 4、6 节）。

3需要调整的设计

① 建"城市地点库"，但库本身也要整理

Nominatim 公共服务限制每秒 1 次请求，也不允许批量抓取。改为：每个支持的城市用 Overpass 或 OSM 数据文件批量提取景点和餐厅，补齐中文名（Wikidata 中文名 + 大模型翻译，结果缓存），存成自己的地点库。生成时让大模型从库里选，可以减少编造地点、加快查询，但不能保证都对：

  • 仍会出错的地方：同名地点匹配错；景区的中心点和入口不在一处；数据过时（关门、搬迁）。
  • 营业时间缺得多：罗马只有约 25% 的地点有营业时间。首版先人工整理每个城市的核心景点（几十个）：别名、入口坐标、营业时间、来源和核对日期。其余地点的营业时间显示"未知"，不让大模型补成确定的事实。
  • 库外地点：截图或搜索中出现库里没有的地点时，给出候选让用户确认，或先放进待安排并标为"待核实"。
  • 首版是"支持的城市"列表，不是任意城市，与原型里的城市下拉框一致。

② 公共交通：只给估算

OSRM / OpenRouteService 只算步行、驾车、骑行。精确的公交地铁路线需要各城市的公交时刻数据和单独的路线服务，首版做不了。地点之间的交通显示为"步行约 9 分钟"或"地铁/公交约 15–20 分钟（估算）"，并提供"在地图中导航"外链。对"候选地点交通比较"的影响：步行、打车距离可以算准，公交只能估算。

③ 餐厅没有评分

OSM 有餐厅的名字、位置、营业时间，但没有评分和评论（Google 地点数据在大陆不可用）。"吃什么"推荐依靠大模型的知识 + 地点库核对餐厅是否存在；详情页不显示评分，显示"来自 OSM 的营业时间，出行前请再确认"。

④ 微信里的导出

微信内置浏览器不能下载文件。长图：生成后在页面上全屏显示，提示"长按保存图片"。Word：提示"在浏览器中打开后下载"。Markdown：直接复制到剪贴板。

4部署方案与成本

阶段做法优点代价
阶段一（推荐先做）香港轻量服务器 + 自己的域名 + HTTPS；页面、地图、图片都放在这台服务器（或香港对象存储）不用备案，几天就能上线；能同时访问国内大模型和海外数据大陆访问速度和稳定性要实测；微信里打开可能出现"非微信官方网页"提示
阶段二（如有需要）大陆服务器 + 已备案域名放前端和地图文件；后端仍在香港大陆访问最快最稳ICP 备案通常需要 1–3 周；个人备案网站能否提供 AI 交互功能有不确定性

大致费用（估算，以下单时为准）：香港轻量服务器每月几十元；域名每年几十元；每个城市的地图约 10–30 MB，存储费用可以忽略；大模型按用量计费，单次行程生成预计几分钱到几毛钱，需用 key 实测。

不建议用 Vercel、Cloudflare Pages、GitHub Pages：它们的默认域名在大陆经常无法访问或很慢。

5地图实测


做法：从 Protomaps 全球底图（约 139 GB，2026-10-08 版）中只切出罗马城区，得到 12 MB 的单个文件；用本地服务器提供，MapLibre 渲染，叠加 3 个编号地点。第一张图的虚线是三点直接相连，只验证了路线图层能显示；第二张图才是沿街道的实际路线。

看到的：街道、绿地、河流清晰；"罗马"、"万神殿"、"特雷维喷泉"等有中文名，其余多为意大利语原名 — 所以我们自己的地点标记和卡片要用地点库里的中文名，不能依赖底图。

沿街道的路线（追加验证）：路线服务除了距离和时间，还会返回整条路线的形状。万神殿→特雷维喷泉（679 m，9 分钟）、特雷维喷泉→斗兽场（1.8 km，24 分钟）两段都沿街道画出，见第二张图（复现：tech-spike/map-rome/index-route.html）。驾车同理。公共交通：OSM 里有罗马的地铁 A/B 线和有轨电车线路的形状（共 25 条），可以按"走到车站 → 沿地铁线 → 走到目的地"画出大致形状，但换乘和时刻仍是估算。

上线前要改：测试页的字体和图标文件还指向 github.io（大陆不稳定），正式版要改成自托管。复现步骤见 tech-spike/map-rome/README.md。

6合规

以下是待核对项，不代表已经合规。

  • 生成式 AI：调用已备案的国内大模型，不等于我们的服务自动合规。需核对：向公众开放时的登记要求、AI 生成内容标识、用户输入的内容安全。作品阶段建议用邀请码或小范围分享。
  • 地图：只展示境外城市可以避开国内地图的审图问题，但是否完全不涉及还需核对。
  • OSM 数据许可（ODbL）：不只是署名。我们的地点库由 OSM 加工而来，属于衍生数据库，若公开分发要按 ODbL 共享；在产品中使用需署名。具体边界需对照 OSM 许可说明核对。
  • 其他数据：维基百科与 Wikimedia 图片（各自的 CC 许可，需署名作者）、Open-Meteo（非商用免费，需注明来源）。
  • 隐私：首版不登录，行程只存在用户自己的浏览器里，服务器只保存生成任务的临时数据。

以上是技术层面的整理，不是法律意见。

7还没验证的，和怎么验证

1. 核心生成流程（最重要）：需要一个国内大模型的 API key（建议 DeepSeek 或阿里云百炼）。跑一个小型完整流程：选三座城市 → 从地点库筛候选 → 生成结构化行程 → 检查必去、排除项、日期和交通约束是否满足 → 修改其中一天 → 保存并重新打开。至少覆盖 4 种情况：普通行程、天数明显不够、有固定预约、导入了重复或库外的地点。记录耗时、费用、失败情况、需要人工修正的内容。"输出能填进页面"不等于"生成可用"。
2. 截图识别：用你手上的 3–5 张小红书攻略截图，测通义千问 VL 能否抽出地点名、匹配地点库、库外地点能否进入"待核实"。
3. 部署验收（香港服务器）：不只测首页，要在大陆网络下跑完整生成流程；地图文件的 Range 请求和 CORS；用 itdog.cn、boce.com 多地测速；请大陆朋友用 4G / 5G 和微信各打开一次。
4. 导出验收：长图里包含地图且不空白；在 iPhone 和安卓上都能生成；微信里长按能保存。
5. 后台任务：生成中刷新页面、关掉再打开，进度能恢复；失败能重试；结果不丢。
6. 路线服务：确定正式使用的服务（OpenRouteService 或自建）后，用同样的地点对重新测。
7. 首版支持哪些城市：建议先做意大利几座主要城市（与原型案例一致），每增加一个城市 = 切一份底图 + 建一份地点库 + 人工整理核心景点。
